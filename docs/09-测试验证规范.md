# 09 · 测试验证规范（必须遵守）

> 面向：插件开发者 / 运维。解决：每次改完代码，如何按"真实用户会怎么用"完成验证，
> 而不是只证明"代码没报错"。本规范吸收上游 deepseek-harness 测试策略
> （见 [上游测试策略-参考.md](上游测试策略-参考.md)）并落地到本项目实际部署形态。

---

## 0. 核心原则：验证真实用户路径，而非自我报告

**什么是"真实用户路径"**：用户实际的操作链——打开浏览器 → 点按钮 → 看到结果/文件落盘。

**反面教材（本项目真实发生）**：修"打开配置文件"时，在容器内用 curl 直接调
`settings.openDocument` RPC 返回 `ok:true` 就判定"已修复"——但用户在浏览器 9488 端口
点击按钮依然"没有反应"。原因：curl 只验证了后端能处理请求，没有验证浏览器侧
前端按钮点击 → fetch → toast/反馈 的完整链路。

**规则**：
1. 修复/新功能必须走一遍"用户会用到的入口"（浏览器点按钮、CLI 敲命令、打开页面）验证；
2. 只证明后端 RPC/API 通 = 未完成验证；
3. 每次验证必须能回答："用户看到的/得到的，和预期一致吗？"

## 1. 验证分层（由低到高，越往上越接近真实用户）

| 层级 | 手段 | 证明什么 | 何时必做 |
|---|---|---|---|
| L0 源码级 | build.mjs 构建通过、tsc 无错 | 代码可编译 | 每次改插件 |
| L1 后端 RPC | 容器内/宿主 curl 调 API，校验返回 JSON | 后端能处理该请求 | 改了后端行为后 |
| L2 文件落盘 | 检查容器内外文件、日志（如 OPEN_LOG、settings.yaml） | 副作用真实发生 | 涉及文件/落盘的功能 |
| L3 浏览器自动化 | Playwright 打开 9488 真实页面，点击/输入/截图断言 | 前端按钮 → 请求 → 反馈全链路 | **涉及 UI 的每次改动** |
| L4 用户视角回归 | 浏览器里按用户操作顺序完整走一遍，检查最终产物 | 交付物符合用户预期 | 发布前必做 |

> 修复/新功能至少做到 L2（后端+落盘）；**涉及 UI 的必须做到 L3**；发布前做 L4。

## 2. 浏览器自动化（Playwright）验证要求

项目使用系统 Chromium + Playwright（`/home/wwt/node_modules/playwright`）。

### 必须覆盖的真实路径（按功能）
- **打开配置文件**：设置页 → 点"打开配置文件" → 断言出现 toast、
  断言 `/workspace/open-here/settings.yaml` 更新、OPEN_LOG.md 追加记录
- **数据源配置**：设置页 → 插件卡片 → 添加/编辑/保存/删除数据源 → 断言 settings.yaml 落库、
  页面折叠为一行
- **故障排查工具**：会话中触发 query_* 工具 → 断言模型拿到正确工具输出
- **LAN 访问**：分别用 `http://127.0.0.1:9488/` 和 `http://192.168.0.127:9488/` 打开，
  管理功能（设置/模型配置）都要可用（trusted-hosts 围栏）

### 断言要求
- 用 `page.waitForSelector` / `waitFor` 等**等待真实 UI 状态**（toast 出现、按钮可点），
  不用固定 sleep 猜测
- 截图留证：`page.screenshot({ path })` 存 /tmp 或 workspace 供复查
- 检查网络请求：`page.on("request"/"response")` 记录 API 调用，确认请求真的发出且 200

## 3. 验证脚本存放

浏览器/接口验证脚本放 `scripts/verify-*.mjs`（node 直接跑），命名如：
- `scripts/verify-open-document.mjs` —— 打开配置文件全链路
- `scripts/verify-settings-card.mjs` —— 数据源卡片增删改查
- `scripts/verify-lan-access.mjs` —— localhost + LAN 双访问

脚本要素：base URL 参数化（默认 127.0.0.1:9488）、打印每步断言结果、非零退出码表示失败。

## 4. 每次改动的最小验证清单

| 改动类型 | 必做验证 |
|---|---|
| 插件源码（tools/settings） | L0 构建 → L1 RPC → L3 浏览器（若涉 UI） |
| 运行时补丁（apply-runtime-fixes） | 重跑脚本幂等 → 容器内 grep 注入标记 → L3 浏览器 |
| 部署脚本（compose/entry/pack） | 容器启动健康 → L2 文件/权限 → 端口 200 |
| SOP/资产文档 | 容器内确认文件存在、内容可读、SOP 引用路径正确 |
| 上游 deepseek-harness 更新 | check-upstream.sh 全 PASS → 重打补丁 → L4 回归 |

## 5. 回归记录

- 每次验证完成，把**验证了什么、怎么验的、结果**记入变更记录文档（docs/CHANGELOG 或 commit 说明），
  尤其记录"真实用户路径"证据（截图/日志/落盘文件），避免下次凭"当时 curl 通过了"下结论。
- 发现的问题按 docs/00 第 8 节变更流程处理。

## 6. 禁止

1. 禁止只用后端 curl/API 验证 UI 相关改动就宣告完成；
2. 禁止用固定 sleep 代替 UI 状态等待；
3. 禁止把"代码没报错"当作"功能验证通过"；
4. 禁止在验证脚本里写死本机 IP/端口（参数化 base URL）；
5. 禁止跳过 L4 直接发布。
