# 00 · 项目开发规范（必须遵守）

> 本项目所有代码与文档**必须**按本规范执行。任何"自由发挥"或与规范冲突的实现，
> 先按本规范做；规范没覆盖的，先问再动手。

---

## 0. 项目定位

**dsh-aiops-kits-offline** = 基于 DeepSeek Harness 的 **AIOps 运维诊断插件集合**，
打包为自包含、可离线运行（x86/arm 双架构）的内网部署。

三条铁律：
1. **不存放第三方项目代码**（deepseek-harness / dshmarket / better-sidebar 等上游项目），
   对上游的修改一律用 `patches/` 补丁记录，不 fork 源码进仓库
2. **离线可用**：内网无 npm / 无外网 / 无需编译即可运行
3. **单一仓库**：所有自有插件与部署材料都在 `dsh-aiops-kits-offline`，插件源码直接入库（不用子模组）

## 1. 目录规范

```
dsh-aiops-kits-offline/
├── app/
│   ├── plugins/                 # ★ 所有自有插件（每个一个子目录）
│   │   └── dsh-aiops-<name>/    #   插件命名：dsh-aiops-<能力>
│   ├── market/                 # 市场数据（offline-market 快照）与第三方市场材料
│   ├── scripts/                # 项目辅助脚本
│   └── xdg-open                # 容器内文件打开兼容
├── docs/                       # ★ 全部文档
│   ├── 00-项目开发规范.md       # 本文档
│   ├── 01..06-*.md              # 各专题文档
│   └── source-guide/           # 源码讲解（历史交付物）
├── patches/                    # ★ 对上游的修改补丁（只放可执行补丁）
│   ├── deepseek-harness/        #   git diff 源码补丁（git apply）
│   └── profile/                 #   profile 配置补丁
├── workspace/                  # 用户空间（容器 /workspace）
├── data/                       # DSH_HOME（运行数据，git 排除）
├── runtime/                    # 编译产物（git 排除）
├── *.sh / *.yml                # 部署脚本与编排
└── README.md
```

## 2. 命名规范

- **项目/仓库**：`dsh-aiops-kits-offline`（已定，不改）
- **插件包名**：`@dsh-tools/dsh-aiops-<能力>`（如 `dsh-aiops-troubleshoot`）；目录 `app/plugins/dsh-aiops-<能力>/`
- **文档**：`NN-主题.md`（两位数字序号 + 中文短名）
- **补丁**：`patches/<上游>/NN-描述.patch`
- **脚本**：kebab-case（如 `build-runtime.sh`、`apply-runtime-patches.sh`）

## 3. 插件开发规范

1. **新建插件**：放 `app/plugins/`，初始化 git 后**移除 .git**（纳入主仓库，不用子模组）
2. **bundle 三要素**（缺一不可）：
   - `dsh.bundle.patch` 指向 `cordis.patch.yml`
   - `lib/` 编译产物入库（**不能 gitignore lib/**）
   - `package.json` exports 完整（`.` / `./client` / `./cordis.patch.yml`）
3. **构建**：统一用 `build.mjs`（host ESM + client factory bundle + tsc），
   外部化 `@deepseek-ai/*`；构建需 `DSH_REPO` 指向 deepseek-harness
4. **安装/更新**：构建 → 同步到 `data/profiles/node_modules/@dsh-tools/<插件>/`（受保护副本）→ `docker compose restart dsh`
5. **受保护插件**（内置不可卸载）：不进 profile dependencies，放共享 fallback 目录
6. **配置**：数据源等用户配置走 **settings 命名空间**（Web 卡片），不用硬编码
7. **敏感值**：`role('secret')` + `env:<NAME>` 引用，机密不落盘
8. **工具输出**：必须 **lossless JSON**（浮点/大数转字符串、无 undefined 属性、无 NaN/Infinity）

## 4. 修改上游（补丁规范）

对 deepseek-harness 等上游的任何修改：
1. **改源码**（如 `packages/.../src/*.ts`）→ `git diff` 导出到 `patches/<上游>/NN-描述.patch`
2. **改运行时**（构建产物/配置）→ 写进 `scripts/apply-runtime-patches.sh`（幂等，可重跑）
3. **改 profile 配置** → 存 `patches/profile/NN-描述.patch.yml`
4. 上游更新：`git pull` → 重新 `git apply` 补丁（冲突手动解决）→ `build-runtime.sh` → `apply-runtime-patches.sh`
5. **禁止**：把上游源码 fork 进本仓库、或直接改 runtime 产物而不留补丁

## 5. 文档规范

1. 所有文档放 `docs/`，按 `NN-主题.md` 编号
2. 每个文档开头一句话说明**面向谁、解决什么**
3. **真实为准**：命令、路径、配置必须与实际部署一致；改代码同步改文档
4. **架构图/流程图**：用 Mermaid（.mmd + 生成的 PNG 放同目录 images/）
5. README.md 保持项目总览（目录结构 + 快速开始），详细内容指向 docs/
6. **过时文档**：标注"基于版本 X，当前为 Y"（如 docs/source-guide 标了 rc.7）

## 6. Git 规范

1. **提交信息**：`<type>: <中文摘要>`，type 用 feat/fix/chore/docs/refactor
2. **禁止提交**：`.env`、`data/settings.yaml`（含密钥）、`runtime/`、`node_modules/`、`*.tar.gz`、`.dsh-state/`、`workspace/open-here/`
3. **单一仓库**：插件源码直接入库；不用子模组（子模组引用会导致 clone 缺文件）
4. **推送前**：泄漏检查（`git ls-files | xargs grep -lE "sk-|BEGIN PRIVATE|ghp_"`）
5. **打 tag**：发布时 `git tag vX.Y.Z` 固定版本

## 7. 安全规范

1. 密钥/token 只在 `.env`（git 排除），代码用 `env:<NAME>` 引用
2. 工具返回**永不回显凭据**；错误信息脱敏
3. 对外暴露：dsh web 保持 loopback，端口暴露由 compose 控制；settings/credentials 仅 loopback 可管理
4. 修改上游安全相关代码（如 trust fence）必须在补丁里注明原因

## 8. 变更流程（新功能/修复）

```
1. 新建/修改插件 → 按第 3 节规范开发
2. node build.mjs 构建 → 同步受保护副本
3. 浏览器自动化验证（Playwright，LAN + localhost 都测）
4. 更新 docs/ 对应文档
5. git add + 泄漏检查 + commit（规范信息）+ push
6. 需要发布时：npm pack / 更新离线市场 / 打 tag
```
